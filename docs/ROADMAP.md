# Implementation roadmap

Each phase ends with: green automated tests, a runnable app, a Git commit (or several), and a phase report (features, files, DB changes, tests run / passed / failed, limitations, outstanding work, run commands, next phase).

| Phase | Scope | Exit criteria (tests that must pass) |
|---|---|---|
| **0: Environment and architecture** | Git repo, docs, toolchain install, Laravel and React scaffolds, `.env.example`, PostgreSQL dev and test DBs, lint/format config, Tailwind brand theme | Backend health endpoint returns 200; `php artisan test` and `npm test` run green on an empty suite plus smoke tests |
| **1: Foundation** | Public site (Home, About, Cambridge, CBC, Courses, Exam Centre, Pricing, Contact, Terms, Privacy, Login, Register), Sanctum SPA auth, registration (parent / learner / teacher-by-invite), email verification, password reset, profiles, roles and permissions, account suspension, consent capture, admin user-management foundation, audit log, seeders (roles, permissions, first admin from env vars, clearly labelled demo data) | Registration, login, logout, reset, rate limiting, role-gated endpoints return 403, suspended user is blocked, admin user CRUD |
| **2: Curriculum** | Curricula, level tree, subjects, curriculum-subjects, units, topics, objectives; admin CRUD with drag ordering; curriculum-specific labels; seed of the *structure* only (stage and grade names, no copyrighted content) | Cambridge and CBC CRUD, label rendering, editor vs admin permissions, cascading-delete protection |
| **3: Learning** | Courses, lessons, sections (rich text, examples, diagrams, video embeds), resources (secure uploads), publish workflow and editor approval, enrolment, entitlement checks, progress tracking, resume, bookmarks | Enrolment access, unpublished content hidden, upload validation, progress and resume |
| **4: Examination engine** | Question bank (8 types), marking schemes, assessment builder, random selection, timed attempts, autosave, navigation and review, submit (idempotent), auto-marking, teacher marking queue, feedback, result release, attempt limits, availability windows | Every question type auto-marks correctly; manual marking flow; no answer leakage before release; duplicate submit; expiry auto-submit; attempt limits |
| **5: Dashboards and reporting** | Learner, parent, teacher and admin dashboards (distinct layouts); charts; topic performance; revision recommendations (rule-based from real results); notifications (database + mail); announcements; PDF progress reports; certificates | Parent sees only linked children; teacher sees only assigned classes; recommendations derived from fixtures |
| **6: Subscriptions and payments** | Plan admin, entitlements, M-Pesa STK Push (sandbox), card gateway (sandbox), callbacks, server-side verification, receipts and invoices, expiry and renewal, reconciliation, payment history | Callback idempotency, forged callback rejected, frontend-only "success" does not activate, expiry job, entitlement gating |
| **7: Security and QA** | Permission matrix tests, OWASP checks (XSS in rich text, IDOR on uuids, upload abuse, rate limits), DB integrity, load test of exam autosave, Playwright mobile viewports, accessibility audit (axe) | Full suite green; documented security review |
| **8: Production preparation** | Truehost VPS review, Nginx + PHP-FPM + Supervisor + cron, Let's Encrypt, `elite-revision.com` DNS, backups (DB dumps + file storage, off-site, restore test), log rotation, monitoring, deploy and rollback scripts, runbook | Staging deploy verified; restore drill done. **No production deploy without explicit approval.** |

## Realistic sizing

This is a large product. As a rough guide for one developer working with AI assistance: Phases 0–1 take days, Phases 2–4 take several weeks, and Phases 5–8 take several more weeks. The brief's insistence on tests and genuine functionality is the right call. It also means no phase will be skipped or mocked to look finished.
